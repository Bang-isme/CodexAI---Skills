# v18.1.0 Onboarding and Artifact Layout Design

## Goal

Make CodexAI Skill Pack easier to understand, install, and use across its supported hosts while producing fewer irrelevant files in consumer projects. Keep product claims tied to checked behavior and preserve the existing host and artifact paths wherever possible.

## Audience and constraints

- Primary audience: developers installing and using the pack in Codex, Claude Code, Cursor, or Antigravity.
- Keep all four adapters equally visible in onboarding; describe each host's actual integration level.
- Do not require GitHub CLI for core skills. GitHub CLI is optional for workflows that call GitHub.
- Do not require third-party skills or a distillation file.
- Avoid broad migration of existing `.codex/` artifacts in this release.

## Design

### Onboarding and installation

- Rewrite the repository README as a short product landing page: what it does, first commands, supported hosts, concrete limits, and links to installation, Vietnamese usage, and technical internals.
- Put host setup details in one installation guide with the same prominence for Codex, Claude Code, Cursor, and Antigravity. Distinguish native plugin, rules/skills adapter, and candidate integrations honestly.
- Make installation of one explicit host the default path. `all` remains available only as an explicit choice.
- A user-scope install must not write a bridge into the shell's current directory. A project-scope install writes only that project's host integration files.
- Remove GitHub CLI from required plugin tools metadata; document it only for GitHub-dependent workflows.

### Generated project structure

- Keep the existing domain folders under `.codex/` and document their purpose, producer, and lifecycle in one artifact map.
- Treat `.agents/`, `.claude/`, `.cursor/`, and Antigravity plugin paths as host integration, not project work-product folders. `.codexai/` is reserved for the generic host harness.
- Create folders only when the selected workflow needs them. Do not scaffold every role, unused folder, placeholder, or duplicate output by default.
- Change role-doc initialization so the default creates only `PROJECT-BRIEF.md` and the ADR template. Users can request selected roles with `--roles frontend,qa` or all roles explicitly with `--roles all`.
- Add a concise repository-structure rule to the always-loaded workflow baseline and link the existing file-structure reference for deeper guidance.

### Versioning and package contents

- Set source, host manifests, generated adapter metadata, README, and changelog to `18.1.0` consistently.
- Keep developer-only specs and plans out of customer release archives.
- Do not claim that these changes prove generated interfaces are beautiful or that host integrations are live-tested.

## Acceptance criteria

1. Root README is at most 120 lines and links every deeper setup/reference page.
2. Users can identify one install command/path per supported host; no installer path silently installs all hosts.
3. User-scope installation creates no project bridge or host files in the current working directory.
4. Default role-doc initialization creates exactly two common files and no role subfolders; explicit selected-role and `all` modes remain functional and idempotent.
5. New project work follows existing conventions and creates only task-relevant directories; artifact locations and lifecycles are documented.
6. GitHub CLI is described as optional and absent from required plugin tool metadata.
7. All version-bearing manifests agree on `18.1.0`; local validation and release archive dry run pass.

## Out of scope

- Moving existing user data or renaming established `.codex/` paths.
- Publishing to any marketplace, creating a paid store listing, or claiming commercial readiness.
- Certifying live behavior in host applications that are unavailable in the development environment.
